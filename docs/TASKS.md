# Pet Agent 项目任务

> A：Agent / 模型；B：后端 / 数据库 / 地图服务；C：前端 / 交互 / 演示。接口细节见 [API 约定](API.md)，技术选型见 [TECH_STACK.md](TECH_STACK.md)，提审规则见 [PR 指南](PR_GUIDE.md)。

**P0** 先跑通“保存宠物资料 → 向 Agent 提问 → 结合资料回答”并补齐会话上下文；**P1** 优先日常记录、站内提醒和 Agent 查询，同时保留原定附近宠物服务；**P2** 为就诊摘要等增强功能，按余力领取。原有任务编号和完成状态不因新增计划而重置。

P0 宠物资料字段已决定采用 `birthday` 和 `notes`，不新增 `age`、`health_notes`。具体规则见 [API 约定](API.md#p0-最终决定生日和备注字段)；P0-0 中的其他接口内容仍需共同确认。

## 状态怎么维护

- 使用 `未开始`、`进行中`、`待审核`、`已完成`。负责人领取后更新状态，提 PR 后填链接并标为待审核。
- 任务表保存在 Git 分支中：在功能 PR 里修改状态，在该 PR 合并前不会出现在 `main`。未合并期间的实时进度以对应 Issue 和 PR 为准，不把分支里的状态当成主分支已更新。
- 有代码的任务在对应 PR 合并、必要验证通过后标为已完成；共同确认类任务由 A、B、C 都确认后完成。一个任务可以拆成多个小 PR。
- 下表为根据当前 `main` 整理的初始快照；团队成员如已在其他分支工作，请自行更新状态，避免重复开发。
- 接口变更先通知 A、B、C，更新契约草案；至少一名其他成员评审，涉及接口的任务由使用方确认。
- 任务编号用于跟踪工作，**不等于 GitHub 的 PR 编号**。PR 先合接口、再合功能；每个 PR 保持独立、可启动和可验证，按 PR 指南小步拆分并尽量每日合并。

## P0 收尾补充：会话上下文修复

| 编号 | 任务 | 主责 / 协作 | 建议审核 | 依赖 | 状态 | 完成标准 |
|---|---|---|---|---|---|---|
| P0-8 | 同一会话历史传入模型 | A/B 主，C 协作 | A/B 互审，C 验收 | P0-4、P0-6 | 未开始 | 同一会话能理解追问，不同会话互不混用；历史窗口、重启恢复、错误和当前宠物边界通过下列验收 |

当前源码已保存会话和消息，但聊天路由没有把数据库历史传给 `run_chat`；每次请求创建的 Provider 只收到本次问题。复用 `session_id` 不等于模型已获得历史。P0-8 是补充修复，不撤销 P0-4 的模型接入或 P0-6 的页面联调成果；P0-6 状态仍由对应功能/状态 PR 维护。P0-7 最终验收还需覆盖 P0-8。

| 成员 | 具体要求 |
|---|---|
| A | 为 Agent 入口和 Provider 增加历史消息输入；组织“系统提示 → 历史用户/助手消息 → 本次问题”；保持 Provider 按请求创建，禁止使用全局共享对话状态 |
| B | 按 `session_id` 读取数据库历史，稳定地按发生顺序传给 A；本次回复成功后保存本轮；历史中不提前加入本次问题，避免重复 |
| C | 核查首次请求传 `null`、续聊复用返回的 ID、新建会话清空旧上下文；失败时保留原会话 ID；不在本次强制实现刷新恢复 UI 或历史会话列表 |

A/B 先确认内部历史消息结构（`role`、`content`），首版只传历史用户消息和助手最终回复，不重放旧工具调用。建议最多最近 10 个完整轮次，并设置明确总字符上限；上限值在实现 PR 中确认并测试，超限从最早完整轮次移除。数据库历史为上下文来源，对外 `POST /api/v1/chat` 请求/响应格式保持现有约定。

当前请求的 `pet_id` 决定本轮关联宠物；为 `null` 时不因历史自动恢复旧关联。切换宠物后不能把旧宠物资料当成新宠物资料，当前资料仍经工具查询。重复点击、取消后重试及请求失败不能悄悄切换会话；并发发送策略由 A/B/C 明确（首版可在前端同一会话只允许一个请求在途）。

- [ ] 同一会话先说“我给猫起了个昵称叫小煤球”，再问“刚才那个昵称是什么？”，正确回答；另开会话不能带入该昵称。
- [ ] 用 Mock Provider/请求捕获确认模型实际收到历史、顺序正确、本次问题仅出现一次，不只检查页面显示或 ID。
- [ ] 后端重启后，使用已有 `session_id` 仍能读取数据库上下文；不存在的会话仍返回明确错误。
- [ ] 测试历史截断、当前宠物切换/`null`、模型失败以及原有资料工具；前端构建与相关测试通过。

### 实现边界与验收场景

- 记录表示“已经发生”，提醒表示“计划发生”，分开存储；记录不塞进 `notes`，历史不从聊天文本反推入库。
- 首版用户通过表单写入记录/提醒，Agent 只读。工具名可参考 `list_pet_records`、`list_pet_reminders`，最终签名由 P1-7 确认，不在任务表提前冻结接口。
- 记录后可让用户填写下次日期；疫苗、驱虫、用药周期不由模型自行决定。提醒完成不自动伪造护理记录；如提供“一并记录”，需用户明确确认并保持一致性。
- 首版提醒只在进入页面或刷新时查询。到期状态由程序按确认的日期/时区规则计算，不依赖模型计算；关闭程序后的通知、微信/短信及后台调度归 P2。
- 若提醒关联了记录，修改/删除记录时不应留下失效引用；联动或保留规则在 P1-7 明确。删除宠物沿用既有错误约定，不暗中级联清除历史。
- 验收场景：给豆豆添加驱虫记录并设置下次日期 → 待办页显示 → Agent 查询“上次何时驱虫、这周有哪些安排” → 完成待办后刷新仍保留完成状态。另建宠物不能读到豆豆的记录。
- 拆 PR：先契约，再记录后端/页面，再提醒后端/页面，再 Agent 查询及联调；每个 PR 独立可验证，不把真实地图接入混入。

- 寻宠社区及线索匹配：先做 P2-7 信息卡，发布网络、线索审核和位置隐私另行设计。
- 宠物叫声“翻译”、在线诊断、配种/社交/共享遛狗平台：缺少验证能力或用户与可信机制，不作为当前已具备的 Agent 能力。
- 开放式“毒狗地点”标记：需要举报核实、纠错、时效与滥用处理，不直接开放未经核实的公开标记。
