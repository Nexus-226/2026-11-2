# Pet Agent：三人任务拆分（3 天版）

> 目标：3 天内完成一个可演示的 Pet Agent。P0 跑通宠物资料与智能问答；P1 再加入附近宠物医院、洗护店和用品店的地图查询。
>
> **P0 = 项目必须完成的核心流程；P1 = 核心流程稳定后再做的扩展。**优先级对 A、B、C 使用同一标准。

## 1. 分工总览

| 负责人 | 负责范围 | 最终交付 |
|---|---|---|
| A | Agent / 模型 | 能理解用户问题，按需调用后端能力，并生成清楚、可信的回答 |
| B | 数据库 / 业务接口；地图服务为 P1 | 保存宠物资料；有余力时提供附近门店数据 |
| C | 前端 / 交互 / 演示 | 完成可操作页面，串起 A、B 的接口，准备稳定的演示流程 |

## 2. 每个人的任务

### A：Agent / 模型

| 优先级 | 任务 | 完成标准 |
|---|---|---|
| P0 | 编写 Agent 系统提示词 | 明确角色、回答边界和安全提醒；信息不足时主动追问 |
| P0 | 识别用户意图 | 至少区分：普通宠物问答、读取宠物资料 |
| P0 | 定义并接入工具调用 | 能调用 B 提供的宠物资料接口 |
| P0 | 统一回答格式 | 回答简洁；医疗类问题提示“仅供参考，必要时咨询兽医” |
| P0 | 准备测试问题 | 覆盖正常问题、信息缺失、接口失败三类情况 |
| P1 | 增加对话记忆 | 在一次会话中记住宠物名称、品种、年龄等信息 |
| P1 | 接入附近服务查询 | 识别用户寻找门店的意图，调用 B 的附近门店接口 |
| P1 | 优化推荐说明 | 解释推荐理由，例如距离、类别和营业状态 |

### B：数据库 / 业务 / 地图服务

| 优先级 | 任务 | 完成标准 |
|---|---|---|
| P0 | 设计最小数据结构 | 至少包含用户、宠物资料；字段够演示即可，不做过度设计 |
| P0 | 提供宠物资料接口 | 支持读取和保存宠物名称、品种、年龄、健康备注 |
| P0 | 提供核心接口文档与示例 | A、C 可直接联调宠物资料接口 |
| P1 | 接入地图服务 | 根据经纬度查询附近的宠物医院、洗护店、用品店 |
| P1 | 统一门店返回格式 | 返回名称、类别、距离、地址、电话、经纬度；缺失值允许为空 |
| P1 | 准备地图兜底数据 | 地图服务不可用时可返回一组固定演示数据 |
| P1 | 增加筛选和排序 | 支持按类别筛选、按距离排序和限制返回数量 |
| P1 | 增加缓存或请求保护 | 降低重复地图请求，处理超时和调用额度问题 |

### C：前端 / UX / Demo

| 优先级 | 任务 | 完成标准 |
|---|---|---|
| P0 | 完成聊天页面 | 可发送问题、展示加载状态、回答和错误提示 |
| P0 | 完成宠物资料表单 | 可填写并保存宠物基本信息，刷新后仍能读取 |
| P0 | 串联 A、B 接口 | 主流程不依赖手工修改数据即可跑通 |
| P0 | 准备演示入口和数据 | 一键进入演示；准备固定账号和宠物 |

| P1 | 完成附近服务页面 | 地图或列表展示三类门店；处理定位被拒绝、无结果等情况 |
| P1 | 优化视觉与交互 | 增加快捷提问、门店分类筛选、地图标记和移动端适配 |
| P1 | 增加演示辅助 | 提供“重置演示数据”按钮或演示模式 |

## 3. A / B / C 之间的简单接口

P0 接口先固定；P1 的附近门店接口在开始地图功能时确认。联调前不要随意改字段；确需修改时，在群里同步并更新文档。

| 接口 | 提供方 → 使用方 | 最小输入 | 最小输出 |
|---|---|---|---|
| `GET /api/pets/{petId}` | B → A、C | `petId` | 宠物名称、品种、年龄、健康备注 |
| `PUT /api/pets/{petId}` | C → B | 宠物资料 | 保存结果和最新资料 |
| `GET /api/nearby`（P1） | B → A、C | `lat`、`lng`、`category` | 门店列表：名称、类别、距离、地址、电话、经纬度 |
| `POST /api/agent/chat` | A → C | `message`、`petId`、可选位置 | Agent 回复、可选工具调用结果、错误信息 |

统一返回外壳：

```json
{
  "success": true,
  "data": {},
  "message": ""
}
```

约定：

- `category` 使用固定值：`hospital`、`grooming`、`store`。
- 距离统一用米；经纬度使用数字类型。
- 电话、营业时间等第三方数据可能缺失，前端显示“暂无信息”，不要报错。
- 请求失败时返回明确错误码和可读提示；若展示 P1 地图功能，可准备注明来源的演示数据。

## 4. 三天安排

| 时间 | A：Agent / 模型 | B：后端 / 地图 | C：前端 / Demo | 当天共同目标 |
|---|---|---|---|---|
| 第 1 天 | 定提示词、资料工具参数；用假数据自测 | 定数据结构和接口；完成宠物资料接口 | 搭页面框架、聊天框和宠物表单；用假数据开发 | 晚上冻结 P0 接口字段，每人都能独立展示自己的部分 |
| 第 2 天 | 接资料接口；补追问和医疗提醒 | 修复资料接口与存储问题 | 接入资料、聊天接口；补加载和错误状态 | 跑通“填资料 → 提问 → 获得个性化回答”主流程 |
| 第 3 天 | 稳定核心回答；有余力再接附近查询 | 稳定核心接口；有余力再接地图服务 | 彩排核心演示；有余力再展示门店页面 | 先完成 P0 并完整彩排 2 次，再决定是否展示 P1 |

## 5. 轻量 Git 协作规则

1. `main` 始终保持可运行，不直接在 `main` 上开发。
2. 每人使用自己的短分支：`feat/agent`、`feat/backend-map`、`feat/frontend`。
3. 一次提交只做一类事情，提交信息写清结果，例如：`feat: add nearby place API`。
4. 合并前先同步最新 `main`，自己解决冲突并完成最小自测。
5. 通过 Pull Request 合并；至少由另一人快速检查接口字段、启动方式和明显错误。
6. 小步合并，每天至少合并一次；不要等到第 3 天一次性提交全部代码。
7. 密钥放在本地环境变量中，只提交 `.env.example`，禁止提交真实 API Key。
8. 公共接口或数据结构有变化时，先在群里说明，再同时更新接口文档和示例。

## 6. 共同端到端 Demo 验收清单

三人一起按同一条流程验收；以下 P0 全部通过才算完成。

- [ ] 使用固定演示账号进入系统，页面可正常打开。
- [ ] 新建或修改一只宠物的资料，保存成功并能重新读取。
- [ ] 询问一个与该宠物有关的问题，Agent 能结合宠物资料回答。
- [ ] 信息不足时，Agent 会追问，不会编造宠物信息。
- [ ] 医疗相关回答包含必要的风险提示，不冒充兽医诊断。
- [ ] 模型或资料接口失败时，有可读错误提示。
- [ ] 从“打开页面”到“保存资料并获得个性化回答”可连续完成，无需改代码或手工改数据库。
- [ ] README 写明启动方式、环境变量、演示账号和 3 分钟演示步骤。
- [ ] 三人已共同完整彩排至少 2 次，并确认由谁操作、谁讲解、谁处理意外。

P1 地图功能完成后，再共同验收：定位或固定演示位置可用；三类门店能查询；名称、类别、距离和地址可见；缺少电话、拒绝定位或地图接口失败时页面不报错。

## 7. 建议的 3 分钟演示顺序

1. 打开宠物资料，展示已保存的宠物信息。
2. 向 Agent 提一个与宠物年龄或品种相关的问题，展示个性化回答。
3. 简短说明：A 负责智能回答，B 负责宠物数据，C 负责用户体验和完整串联。
4. 若 P1 已完成，再询问“附近有哪些宠物医院？”，展示门店查询。
