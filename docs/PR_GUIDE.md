# Pet Agent：PR 拆分与评审规范（3 天版）

> 配套文档：[接口契约草案](API.md)、[技术栈与分层约定](TECH_STACK.md)
> 目标：接口先合、功能后合；每个 PR 能独立启动、只做一件事、至少一人评审。
> 适用：A（Agent）、B（后端/数据）、C（前端/演示）

---

## 1. 总原则

1. 按竖切拆 PR，不按 A/B/C 各开一个大 PR。
2. 接口 PR 先合，功能 PR 后合。接口契约先冻结，A 和 C 才能并行。
3. 一个 PR 只做一件事。不出现“顺便改了返回外壳还加了地图”的 PR。
4. 每个 PR 必须能独立启动，描述里写清启动命令和验证步骤。
5. 每个 PR 至少一人评审，评审只看四件事（见第 5 节）。
6. 每天至少合并一次，不等到第 3 天一次性提交。
7. P1 高德真实接入单独开 PR，不混进种子数据 PR，失败不影响主分支。
8. PR 中修改的任务状态在合并前不会更新 `main`；审核期间通过对应 Issue 和 PR 查看实时进度。

## 2. PR 拆分清单

| 顺序 | PR 标题 | 内容 | 提交人 | 评审人 | 依赖 |
|---|---|---|---|---|---|
| 1 | chore: 项目骨架与启动说明 | React/Vite、FastAPI、README、.env.example、.gitignore、pyproject.toml、/health（已合并） | B | A 或 C | 无 |
| 2 | feat: 宠物资料 CRUD 与错误格式 | pets 表、`/api/v1/pets` CRUD、统一错误、接口示例 | B | A + C | PR1 |
| 3 | feat: 前端宠物表单 | React 页面、API Client，表单调用 PR2 接口 | C | B | PR2 字段冻结 |
| 4 | feat: Agent 对话接口与资料工具 | `POST /api/v1/chat`、工具调用循环、get_pet_profile 工具 | A + B | C | PR2 接口 |
| 5 | feat: 聊天页面接入 Agent | 聊天 UI、加载/错误状态、调 PR4 | C | A | PR4 |
| 6 | feat: P1 附近门店（种子数据） | 演示数据、`GET /api/v1/nearby`、距离排序、前端列表/地图；明确标注数据来源 | B 主 + C 辅 | A | PR2 |
| 7（可选） | feat: 高德 Adapter | 真实 POI 接入，失败回落种子数据并标注来源 | B | A | PR6 |

PR7 对三天演示可选，不阻塞 P0 或种子数据版 P1 的演示；但只有真实高德接入和相应验收完成，才能称为完整的 P1 附近服务。未完成时应明确说明当前是种子数据演示。

## 3. 分支命名

一个分支对应一个 PR，合完即删。建议命名：

- chore/project-skeleton
- feat/backend-pets
- feat/frontend-shell
- feat/agent-chat
- feat/frontend-chat
- feat/backend-nearby
- feat/backend-amap（可选）

不要长期保留 feat/agent、feat/backend-map、feat/frontend 这类“大分支”，否则 commit 会堆积，评审困难。

## 4. 时间线（与三天安排对齐）

| 时间 | 合并的 PR | 合并后状态 |
|---|---|---|
| D1 晚 | PR1、PR2 | 后端能跑，宠物接口冻结，A/C 可联调 |
| D2 中午 | PR3、PR4 | 前端表单 + Agent 接口都能单独跑 |
| D2 晚 | PR5 | 主流程“填资料 → 提问 → 回答”跑通 |
| D3 上午 | PR6（若做 P1） | 附近门店可演示 |
| D3 下午 | 只修 bug 的小 PR | 不加大功能 |

## 5. 评审清单（评审人只看这四件事）

- [ ] 接口字段一致：以 [API 契约](API.md) 的评审结果为准，包括版本前缀、错误结构、地点类别、坐标和距离单位。
- [ ] 能按 README 启动：按 PR 描述里的命令能跑起来，不依赖未提交的本地文件。
- [ ] 失败路径可读：接口失败返回明确错误码和可读提示，不是 500 裸奔；前端有加载/错误状态。
- [ ] 无敏感信息：未提交真实 API Key、.env、真实定位数据、真实对话数据。

---

## 6. PR 描述模板

每个 PR 使用以下模板，缺项不合并。

目标：一句话说明这个 PR 解决什么。

改动：
- 主要文件/模块
- 新增或修改的接口（如有）

如何启动：
- 写明命令，使用 README 中的 Python 包安装及前后端启动方式。

如何验证：
1. 正常路径：……
2. 空数据：……
3. 失败路径：……

接口变更：
- 无 / 有（列出字段变化，并确认已同步文档和 A/C）

自查：
- [ ] 接口字段与文档一致
- [ ] 正常/空/失败三条路径已试
- [ ] 未提交密钥或敏感数据
- [ ] 已同步最新 main 并自测

---

## 7. 合并规则

1. 从 main 创建短分支，PR 合回 main。
2. 合并前先同步最新 main，自己解决冲突并完成最小自测。
3. 至少一人评审通过后合并；接口类 PR 需 A 和 C 中至少一人确认字段。
4. main 始终保持可启动，合并后由提交人快速验证一次启动。
5. 合并后删除分支，不在仓库保留已合并分支。

---

## 8. 常见错误（避免）

- D3 一次性提一个大 PR，包含前后端和地图。
- 接口字段在 PR 里悄悄改了，没通知 A/C，导致联调失败。
- PR 描述只写“完成功能”，没有启动和验证步骤。
- 把 .env、真实 Key、真实定位提交进仓库。
- 高德接入和种子数据混在一个 PR，高德失败拖垮主分支。
- 评审只看代码风格，不验证启动和失败路径。

---

## 9. 一句话总结

按“骨架 → 宠物接口 → 前端表单 → Agent 接口 → 聊天页 → 附近门店”拆 6 个 PR，接口 PR 先合冻结字段，每个 PR 能独立启动、只做一件事、至少一人按四件事评审，每天至少合一次；高德单独开 PR，不混进种子数据。
