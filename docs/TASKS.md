# Pet Agent 项目任务

> A：Agent / 模型；B：后端 / 数据库 / 地图服务；C：前端 / 交互 / 演示。接口细节见 [API 约定](API.md)，技术选型见 [TECH_STACK.md](TECH_STACK.md)，提审规则见 [PR 指南](PR_GUIDE.md)。

**P0** 先跑通“保存宠物资料 → 向 Agent 提问 → 结合资料回答”；**P1** 在核心流程稳定后增加附近宠物服务。

P0 宠物资料字段已决定采用 `birthday` 和 `notes`，不新增 `age`、`health_notes`。具体规则见 [API 约定](API.md#p0-最终决定生日和备注字段)；P0-0 中的其他接口内容仍需共同确认。

## 状态怎么维护

- 使用 `未开始`、`进行中`、`待审核`、`已完成`。负责人领取后更新状态，提 PR 后填链接并标为待审核。
- 任务表保存在 Git 分支中：在功能 PR 里修改状态，在该 PR 合并前不会出现在 `main`。未合并期间的实时进度以对应 Issue 和 PR 为准，不把分支里的状态当成主分支已更新。
- 有代码的任务在对应 PR 合并、必要验证通过后标为已完成；共同确认类任务由 A、B、C 都确认后完成。一个任务可以拆成多个小 PR。
- 下表为根据当前 `main` 整理的初始快照；团队成员如已在其他分支工作，请自行更新状态，避免重复开发。
- 接口变更先通知 A、B、C，更新契约草案；至少一名其他成员评审，涉及接口的任务由使用方确认。
- 任务编号用于跟踪工作，**不等于 GitHub 的 PR 编号**。PR 先合接口、再合功能；每个 PR 保持独立、可启动和可验证，按 PR 指南小步拆分并尽量每日合并。

## 共同 P0 验收

- [ ] 按 README 在新环境启动前后端，`/health` 正常。
- [ ] 新建、查看、修改和删除宠物资料；页面与接口正确处理空数据及失败。
- [ ] 提出与宠物相关的问题，Agent 通过受控工具读取资料并给出回答。
- [ ] 参数不合法、宠物不存在或模型不可用时，显示清楚的错误；不伪造回答。
- [ ] 对话有加载、取消等待和超时处理；医疗类回答包含必要的风险提示。
- [ ] 核心接口与服务测试通过，前端构建通过；密钥和真实数据未提交。
- [ ] 三人一起从打开页面完整演示核心流程，确认操作人、讲解人和异常处理。
